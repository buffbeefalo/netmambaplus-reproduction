# Research record for the customer package

This is a reviewed record of the questions, source evidence, decisions and executed experiments behind this repository. It shares the useful research from the AI-assisted work; it is not a verbatim private chat export or an independent certification. The [customer index](../customer/README.md) links the measured results and presentation files. The historical [7 September audit](../audit.md) remains dated evidence.

The later [final council review](final-council-review.md) and [acceptance map](../customer/acceptance.md) document the expanded customer guide, repeatability checks, corrections and exact review outcomes. They preserve the original experiment records and distinguish local checks from public release verification.

## The question changed from packet classification to flow reproduction

The starting materials were NetMamba+ paper v1 and two uploaded Payload-Byte CSVs. Their common subject is learning traffic categories from network bytes. Their observation units differ: the CSVs describe packets, whereas NetMamba+ combines ordered bytes, packet sizes and arrival intervals within a flow.

A full CSV metadata scan recorded **1,410,255 CICIDS2017 rows with 15 labels** and **79,881 UNSW rows with 10 labels**. Both have 1,505 columns: 1,500 payload-byte positions, TTL, total length, protocol, time delta and label. Neither schema contains source/destination addresses and ports or an established flow identifier and ordering. Neighboring rows cannot be treated as neighboring packets of one connection. The CICIDS2017 time-delta minimum is **−0.000018** in the stored units. Its smallest label has **12 SQL-injection rows**, versus **362,108 benign rows**. These facts make connection reconstruction and class imbalance material concerns.

The scan checks CSV parsing, row counts and metadata aggregates across the complete files. It does not exhaustively validate every payload byte, deduplicate the packet exports, establish their collection provenance or train a packet classifier. The exact file hashes, label counts and query tool are published with the evidence. No raw packet content is included in this package.

The resulting decision was to use the authors' released, processed **CICIoT2022** flow dataset and original multimodal Mamba implementation. CICIoT2022 is not CICIDS2017. A CSV-based model would be a separate adaptation, not the experiment implemented here.

## What the paper and source actually say

The primary paper is [arXiv:2601.21792v1](https://arxiv.org/abs/2601.21792v1), 16 pages. The inspected implementation is [commit eec9483e2f0fb84ca22982b9de8149bc3a8b1ad2](https://github.com/wangtz19/NetMambaPlus/tree/eec9483e2f0fb84ca22982b9de8149bc3a8b1ad2). Every tracked source file is checked against its Git object before the harness imports its parsers; seven core files have additional SHA-256 pins.

- **Input:** first five packets, 320 stored bytes per packet; first twenty packet sizes and first twenty inter-arrival values. Paper pages 8–10 describe an 80-byte header and 240-byte payload region. The processed JSON must already contain the extraction. Our loader does not manufacture absent headers or connection identity.
- **Encoder:** four unidirectional Mamba blocks, 256-dimensional embeddings, state dimension 16, expansion factor 2 and convolution width 4. Four-byte strides produce 400 byte tokens; sizes, intervals and three summary tokens bring the full classifier sequence to **443 tokens**. NetMambaB is a separate bidirectional variant.
- **Pretraining:** masked reconstruction, with 90% byte masking and 15% masking for each sequence modality in the selected source settings. The paper lists Browser and Kitsune data, 150,000 steps, batch 128 and learning rate 0.001. It reports 149,528 Browser flows and 167,831 Kitsune flows in Table II. This repository has not established those exact pretraining inputs or their processing history.
- **Fine-tuning:** learn a six-class head and update the encoder using labeled training flows; choose the best checkpoint by validation accuracy; then test that checkpoint. The source-based preset uses 120 epochs and batch 128, with `blr=0.002` scaled to a maximum learning rate of **0.001** for one process and accumulation 1. The paper's paragraph specifies batch 64 and learning rate 0.002. These are explicit protocol differences.
- **Reported accuracy:** Table IV, page 11, lists NetMamba+ CICIoT2022 accuracy **0.9750** and F1 **0.9750**. The neighboring byte-only NetMamba entry is 0.9779; it must not be substituted for the multimodal result.
- **Reported online system:** the 261.87 Mb/s average throughput and 3.15-second average batch latency on page 14 describe the paper's byte-only NetMamba online prototype. They do not measure this NetMamba+ port, the current GB10, an NPU, or network interface line rate.

The [pinned README](https://github.com/wangtz19/NetMambaPlus/blob/eec9483e2f0fb84ca22982b9de8149bc3a8b1ad2/README.md) releases pretraining checkpoints and processed fine-tuning datasets. Its environment specifies Torch 2.2/cu121, while the paper describes Torch 2.1.1 and A100 hardware. Matching a paper's model name therefore does not establish an exact runtime or protocol reproduction.

## Why the pretrained file is not an IDS classifier

The externally obtained `fuse3_mamba.pth` has SHA-256 `16e5a7f61c55a5be7a3feb535a59cbb780817f42f29a5840ea34841da243b5d9`. Initial static inspection found reconstruction decoders and no classification head. The current work additionally loaded the trusted file in Torch and checked all classifier-matching shapes. Exactly `head.weight` is absent; the extra reconstruction parameters are expected. No matching backbone tensor has a shape conflict.

Its stored `epoch=40` and `steps=100000` fields are recorded claims inside a checkpoint, not proof of the complete earlier history. The main experiment uses it through the authors' intended transfer-learning path. A new six-output classifier is trained. Only that resulting classifier is eligible for strict inference, with a hash-bound class mapping.

## What failed during installation, and what corrected it

The available host is an aarch64 NVIDIA GB10 with compute capability 12.1 and CUDA toolkit 13.0.88. The old stack was not assumed compatible. An isolated Python 3.12.3 environment uses Torch 2.9.1+cu130, torchvision 0.24.1, Triton 3.5.1, NumPy 1.26.2 and timm 0.4.12. This is a **compatibility port**, not the paper's A100 environment.

1. The old native setup scripts target architectures 70/80/90. Disposable source copies were changed to build `sm_121`; the verified authors' checkout remains unchanged.
2. The causal-conv1d 1.1.2.post1 PyPI source archive has no CUDA `csrc` tree. Its build failed. The full [matching Git tag](https://github.com/Dao-AILab/causal-conv1d/tree/d1ab53ddf93b868502da96ad82c5fc0b270911f5) supplied the missing files; both Python files matched the archive.
3. The bundled Mamba source failed against removed CUB APIs. One `cub::LaneId()` and three `cub::CTA_SYNC()` calls were replaced with the equivalents specified by [NVIDIA's CCCL migration guide](https://nvidia.github.io/cccl/cccl/3.0_migration_guide.html), plus the required include. The model's Python algorithms were preserved. An initial patch-count assertion failed, and a subsequent build before that correction repeated the compiler failure; both attempts are retained in the local build record.
4. Triton's bundled CUDA 12.8 assembler rejected `sm_121a`. Setting `TRITON_PTXAS_PATH=/usr/local/cuda/bin/ptxas` selects the installed CUDA 13 assembler. No Triton model code was rewritten.
5. The old fine-tuner's checkpoint loading predates Torch's changed `weights_only` default. A process-scoped `TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD=1` was used for the already hash-checked research checkpoint. This is not safe loading of arbitrary untrusted pickle files. The model-only export removes the optimizer and argument namespace and can be read with `weights_only=True`.

The exact replacements and pre/post hashes are recorded in the build evidence and automated by [build_gb10.py](../../tools/build_gb10.py). Seven synthetic GPU checks compare causal convolution, selective scan, fused RMS normalization and full Mamba-block forward/backward paths with their reference implementations. FP32 tolerances were `rtol=0.001, atol=0.0002`; FP16 tolerances were `rtol=0.01, atol=0.002`. These checks passed in the measured environment. They establish tested numerical agreement, not equality across all shapes, GPUs or training histories.

Two package-check warnings are preserved: the cuSPARSELt 0.8.0 wheel advertises a nonstandard `sbsa` platform tag despite containing an aarch64 ELF library, and old causal-conv1d declares an uninstalled `buildtools` dependency. The native extensions are explicitly built without dependency resolution. Neither warning is presented as a clean `pip check`; the executed kernel and training evidence is the basis for the narrower runtime claim. Torch also emits a 12.1-versus-12.0 compiled-capability warning on this GB10. These old dependencies are a research environment, not a production support commitment.

## Experiments, selection and test access

The [execution plan](execution-plan.md) fixed seeds **0, 1 and 2**, 120 epochs each, the original source-based preset, and validation-based checkpoint selection before final test scores. **Seed 0** was designated for the demo before those scores. No seed or learning-rate search was performed in response to test performance.

The complete official split was preserved: **8,323 training / 1,040 validation / 1,041 test flows**, with six classes. Exact stored `[data, sizes, intervals]` fingerprints reveal five shared train/validation inputs and six shared train/test inputs. Recorded `pcap_file` identifiers do not overlap. These checks neither establish physical capture independence nor rule out additional equality after truncation and normalization. The released checkpoint's earlier exposure to test-related traffic remains unknown.

Masked pretraining was exercised on **training-only CICIoT2022** data as a functional test. The source rounds its step request to whole epochs: requested 100 steps became **two epochs and 132 completed optimizer updates**. Average epoch loss decreased from about **9.52 to 6.13**, and a checkpoint was saved at zero-based step 130, after 131 updates. The run took **21.07 seconds**. This proves operation of the masked-learning path on these downstream inputs; it does not reproduce the paper's Browser/Kitsune pretraining.

All three main fine-tuning runs completed 120 epochs with finite logged losses. With the native 66 batches per epoch, accumulation 1 and non-AMP optimization, that is **7,920 updates each**. The result collector inspected actual AdamW step counters in the selected checkpoints, verified changed transferred parameters and finite saved tensors, and checked the selected epochs against the complete validation histories. An additional training-only batch on disposable model copies produced finite gradients and an actual head update for every seed; those disposable updates were never used for evaluation or exports.

Test accuracy was **91.26%, 84.05% and 84.63%** for seeds 0, 1 and 2. The mean was **86.65%**, sample standard deviation **4.00 percentage points**. The mean is 10.85 points below the paper's reference; the demo's preselected seed is the highest-scoring of these three. The source protocol and GB10 port executed, but the paper's accuracy was not reproduced. The cause of the seed variation and accuracy gap has not been isolated; the known protocol/runtime differences are not proven explanations.

The native fine-tuner's per-epoch log says “test samples” when the supplied loader is actually validation. The real test loader is created only after training. After that permitted final pass, fresh strict evaluation and recorded inference use the same frozen checkpoint and same test set to verify reproducibility. Those repeated executions are not additional independent holdouts and do not drive further model selection. Confusion matrices and support-weighted metrics must agree, and metrics are independently recomputed from retained predictions.

See [the measured results](../customer/results.md) for all attempted seed runs, their completed status, exact scores, per-class errors, checkpoint hashes and separately measured model-only latency. Training runs shared one GPU; their elapsed times are not isolated throughput benchmarks.

## What is a demonstrated system, and what remains a proposal

The delivered replay displays predictions from a real saved-classifier GPU inference run. It does not capture network traffic, implement a production flow cache, produce calibrated attack probabilities, or block packets. The six labels cover two attack categories and four IoT power/device categories; they are not a universal benign/malicious taxonomy. All mistakes remain visible.

The separate unlabeled-flow command was actually tested after removing labels and capture identifiers from the first 128 test records. All 128 class predictions agreed with the recorded classifier inference. Logits were not bitwise identical: the largest absolute difference was 0.001953125. The benchmark independently observed the same maximum logit difference and complete class agreement between single-flow and batched calls on these inputs. Neither check establishes equivalence for every possible flow.

The first browser rehearsal found horizontal overflow at a 390-pixel viewport. A display-only CSS correction fixed the grid panel's minimum width, and a new HTML rendering retained the original prediction JSON exactly. The subsequent desktop/mobile rehearsal passed playback, filtering, reset, JavaScript-error and overflow checks. A recorded walkthrough and screenshots come from that successful rehearsal; the original failed attempt remains in local run storage.

Final shape review used the measured benchmark inputs and original loader: the byte tensor is `[B, 1, 1, 1600]`, not the 40-by-40 layout initially assumed in presentation drafts. The source model flattens the bytes for four-byte stride embedding. The final lesson, briefing and slides use the observed shape.

The saved classifier ran eagerly on the GPU before an actual strict Torch graph-export probe. Export failed on the custom `causal_conv1d_cuda.causal_conv1d_fwd` call with `Unsupported`. This identifies the first observed graph-capture blocker; it does not test an NPU compiler or establish that all remaining operations can be exported.

A future IDS needs a specified capture/flow policy, original-compatible extraction, controlled online validation, alert handling and operational measurements. Upstream extraction helpers have hardcoded paths and a missing `dataset_debias_common` import; they are not a turnkey, verified live pipeline here. The upstream `--eval` branch and some optional criterion paths also need care: the separate strict evaluator avoids an uninitialized loader in `--eval`, and the training engine replaces a passed criterion with label-smoothed cross entropy. The tested profile does not enable LDA or class balancing and makes no claim about those ablations.

[The hardware roadmap](../customer/hardware-roadmap.md) separates SmartNIC packet handling from accelerated classification. [DOCA Flow](https://docs.nvidia.com/doca/sdk/doca-flow/) supports steering and packet-processing actions; that does not imply a Mamba model runs on the NIC. [DOCA GPUNetIO](https://docs.nvidia.com/doca/sdk/doca-gpunetio/) currently documents that DGX Spark does not support GPUDirect RDMA, so a zero-copy RDMA path is not assumed for this host. [OpenVINO's NPU documentation](https://docs.openvino.ai/2026/openvino-workflow/running-inference/inference-devices-and-modes/npu-device.html) provides one named future compiler/device family to investigate; it does not certify this custom CUDA Mamba implementation as supported.

> Adopt a bounded, staged plan for actual NetMamba+ fine-tuning, saved-classifier inference and the customer package due 15 September 2026. Begin with a GB10 viability pilot, select the execution route by 12 September, and freeze reviewed measured artifacts by 14 September, using America/Los_Angeles dates. Current evidence supports the offline harness, documented source checks, native-data validation and parser dry runs. GPU execution and expanded scientific or deployment claims require the acceptance evidence below. This verification decision does not certify completed experiments or replace the earlier ESCALATED/UNRATIFIED audit.

The [canonical JSON](council-decision.json) and [reviewed ratification receipt](council-receipt.json) are retained. The receipt records both seats' acceptance of that exact hash; the draft-era wording within the immutable artifact is not a substitute for its final ratification state. This was a bounded plan review based on the evidence available at intake. The implementing session performed the subsequent work and verification directly under the user's authorization. The decision is not an independent post-training audit, an approval of future numerical results, or a hardware certification. Earlier ESCALATED/UNRATIFIED records remain unchanged.
